# Varnis — Frontend ↔ Backend Integration Map

Generated by comparing `assets/js/api.js` (the frontend's API contract, as
documented in its inline comments) against `Varnis_API__v1_.yaml` (the live
Django backend's OpenAPI spec), August 2026.

The adapter in `assets/js/api.js` (`PATH_MAP`, `NOT_ON_BACKEND`,
`unwrapEnvelope`) implements everything in **Section 1** automatically — you
don't need to touch page code for these. **Section 2** is flagged to
gracefully fall back to mock data with a console warning, so pages don't
break, but the feature isn't actually live yet. **Section 3** needs real
design decisions, not just a path rename.

---

## 0. Two structural differences the adapter handles everywhere

1. **Response envelope.** Every backend response is
   `{ success, message, data }`. The adapter unwraps `data` automatically so
   the rest of the frontend sees the same shape it always expected.
2. **Trailing slashes.** Django/DRF routes end in `/`
   (`/api/v1/auth/login/`, not `/api/v1/auth/login`). The adapter adds these
   for every path it rewrites.

## 2. Not implemented on the backend yet (forced to mock, flagged in console)

These calls are intercepted by `NOT_ON_BACKEND` in `api.js`. In live mode
they still serve local mock data (so the page doesn't break) but log:
`[VarnisAPI] METHOD /path is not implemented on the backend yet — serving mock data.`

| Feature | Frontend calls | What's missing |
|---|---|---|
| OTP verification | `POST /auth/otp/verify`, `POST /auth/otp/resend` | No `/auth/otp/*` routes in the spec at all. Registration flow (`FR-AUTH-05`) can't actually gate on OTP yet. **When these are built:** email is the default OTP delivery channel everywhere in the frontend — no SMS gateway exists yet. `register.html` sends `otpChannel: "email"` whenever the user supplied one (`"phone"` only if they didn't). `login.html` applies the same rule on the way into its own OTP step: it prefers the account's real email (from the login response) over whatever the user actually typed as their identifier, so someone who logs in with their phone number still gets the code by email if their account has one on file. The backend should honour `otpChannel` and, until SMS is live, send by email regardless of that value whenever a user has one (defense in depth against a stale client). `otp.html` reflects whichever channel is active (heading, icon, and which identifier `verifyOtp`/`resendOtp` call with) — no frontend changes needed once the routes exist. |
| Logout | `POST /auth/logout` | No server-side logout/blacklist route. Harmless to leave mocked — the frontend already clears the local session either way. |
| Notifications | `GET /notifications`, `/unread-count`, `PATCH /notifications/:id`, `POST /notifications/read-all` | No `/notifications` resource in the spec. The whole in-app notification center (`FR-NOT-01..03`) has no backend yet. |
| National alerts | `GET/POST /alerts` | No `/alerts` resource. (Note: `/national-update/` exists and is *similar* in spirit but not the same thing — see §3.) |
| Daily challenge | `GET /challenges/today` | No `/challenges` resource. `/learning/daily-tip/` exists but is a tip, not a scored challenge. |
| Global search | `GET /search?q=` | No `/search` route. |
| Support chat | `POST /support/chat` | No AI/agent chat route. |
| Support channels | `GET /support/channels` | No route — this is static contact info (phone/email/SLA), consider just hardcoding it in the frontend instead of an API call. |
| Ticket replies | `POST /support/tickets/:id/messages` | Backend's `/support/tickets/{id}/messages/` is **GET-only** — no way to post a new message yet. |
| Ticket status | `PATCH /support/tickets/:id` | No generic status PATCH — backend only has `/assign/` and `/close/` actions. |
| Admin user management | `GET /users?role=&status=`, `PATCH /users/:id` | No `/users` admin list/edit route. The Blaise-style admin panel for managing accounts has no backend yet. |
| Community moderation | `PATCH /community/posts/:id` | No generic moderate PATCH — see §3 for the actual (differently-shaped) routes that exist. |
| Device/vehicle recovery | everything under `/recovery/*` | Entire module renamed and restructured server-side as `/tracking/*` — not a simple path swap, see §3. |
| KYC document types | `GET /kyc/document-types` | No route — likely fine to hardcode in the frontend (it's a static list). |
| KYC draft/submit | `PUT /kyc/me/draft`, `POST /kyc/me/submit` | Backend uses a different two-step flow — see §3. |
| KYC review | `PATCH /kyc/submissions/:id` | Backend splits this into `approve/` and `reject/` actions — see §3. |
| Course quiz | `GET/POST /learning/courses/:id/quiz` | Backend's quiz model isn't attached to a "course" the same way — see §3. |

## 3. Needs a real design/backend decision (not a path rename)

These are cases where the frontend's and backend's *data models* diverge,
not just their URLs. Picking the wrong mapping would silently corrupt data
or misrepresent state, so the adapter leaves these on mock rather than guess.

- **Incident submission body.** Frontend sends
  `{category, title, description, district, location}`. Backend's
  `SubmitIncident` wants `{category_id, description, evidence_urls,
  location_shared, latitude, longitude, is_anonymous}`. There's no `title`
  or `district` field on the backend at all, and `category` needs to become
  a numeric `category_id` (presumably from a categories lookup that isn't
  in the spec either). **Decide:** does the backend add `title`/`district`,
  or does the frontend's report form change to match?

- **Leaderboard scope params.** The frontend's single `?scope=` call needs
  to become three different UI states that also pass a `region` code or
  `institution_id` — the frontend doesn't currently collect either.

- **Community posts.** Frontend's generic "post" (`{title, body,
  category}`, moderated via a generic PATCH) doesn't match the backend's
  actual shape: separate `/community/tips` (create), `/community/posts/:id/like`,
  `/comments`, `/report`, plus **admin moderation lives in a completely
  different namespace** — `/console/community/posts/{id}/decision` and
  `/console/moderation/reports/{id}/review` — not under `/api/v1/community/`
  at all.

- **Device/vehicle recovery → "tracking".** This is the biggest gap. The
  frontend's recovery flow (fees, catalog, ownership verification by
  matching 2-of-3 fields, cases with a `stage` field, payment proof upload)
  has no equivalent shape on the backend. The backend instead has
  `/tracking/requests/` with a state machine driven by admin actions
  (`mark-located`, `mark-recovered`, `mark-under-investigation`,
  `ownership-verification`, `request-evidence`, `evidence-requests/{id}/fulfill`).
  These are conceptually related but not interchangeable — this needs a
  dedicated design pass, ideally with whoever owns each side in the room.

- **KYC draft/submit/review flow.** Frontend: one record that moves
  `draft → submitted → approved/rejected` via `PUT .../draft` then
  `POST .../submit`. Backend: `POST /kyc/submissions/` (create) then
  `POST /kyc/submissions/{id}/submit/` (submit) — a two-step, ID-based flow
  — and review is two separate actions (`approve/`, `reject/`) rather than
  one PATCH with a `decision` field.

- **Learning / quiz structure.** Frontend treats a "course" as the unit
  that has one quiz. Backend's structure is deeper:
  `zones → modules → lessons → lesson parts`, with quizzes as their own
  resource (`/quizzes/{quiz_id}/`) reached via a lesson, not a course.
  The Learning Academy pages will need real rework here, not just new
  URLs — this is worth scoping as its own task.

- **Auth token field names.** The OpenAPI spec's `AuthSuccessResponse.data`
  is untyped (`additionalProperties: {}`), so the exact key names for the
  access/refresh tokens inside a login response aren't pinned down by the
  spec itself. I made `persistAuth()` and `tryRefresh()` accept either
  SimpleJWT's usual `access`/`refresh` or the frontend's original
  `token`/`refreshToken` — **check a real login response in devtools once
  this is live** and simplify that code to whichever it actually is.

- **Registration's ID card upload.** Frontend sends an `idCard` (base64
  file) with registration for identity verification. Backend's `Register`
  schema has no such field — worth checking whether that's meant to be a
  follow-up KYC submission instead, since a KYC module already exists.

## 4. On the backend, unused by the frontend (fyi, not blocking)

Your backend has significant surface area the current frontend never
calls — worth knowing about so nothing gets rebuilt by accident:

- **Payments module** (`/payments/config/`, `/payments/submissions/`,
  admin approve/reject/request-proof) — a full proof-of-payment review
  flow. The frontend's `certificates.html` currently has no purchase step
  at all; `FR-CERT-02` (payment before certificate release) isn't wired up.
- **Console CMS** (`/console/zones`, `/console/lessons`, `/console/legal/articles`,
  `/console/national-updates`, `/console/moderation/*`, `/console/audit-logs`)
  — a whole admin content-management layer with no frontend screens yet.
- **Security sessions** (`/security/sessions/mine`, `/revoke-all`,
  `/revoke/:id`) — device/session management, not surfaced in Settings yet.
- **Legal resource center** (`/legal/topics`, `/legal/articles`) — backend
  is ready; `FR-LAW-01..06` isn't wired into the frontend's legal pages yet
  (worth checking if `public/` has a legal-resources page at all).

## Changelog

- **CORS is currently blocking every live request.** Confirmed directly:
  the backend returns `200 OK`, but with no `Access-Control-Allow-Origin`
  header, so the browser refuses to expose the response. This is a Django
  setting (`django-cors-headers`), not something fixable from these files —
  add `CORS_ALLOWED_ORIGINS` (including your dev server's exact origin,
  e.g. `http://127.0.0.1:8000`) in `settings.py` and redeploy. Until that's
  done, every live-mapped call in §1 will fail with a network error and
  quietly behave like an offline mock-fallback — so "the site feels
  disconnected" right now is a backend config gap, not a frontend one.
- **Logout links were never actually wiring up**, root cause found: the
  sitewide "Logout" `<a>` tags render their icon via a font ligature — the
  literal text inside that icon `<span>` is the word `logout` — so
  matching against the link's full `textContent` produced
  `"logoutLogout"`, which never equals `"Logout"`, and the click handler
  silently never attached. Fixed to check only the actual label `<span>`.
  (Network failures like the CORS block above were already handled
  correctly — `logout()` clears the session locally either way — so this
  was purely a selector bug, not a resilience gap.)
- **`USE_MOCKS` flipped to `false`.** The site now calls
  `https://varnis.up.railway.app/api/v1` for real on every page. Anything
  in §1 (mapped) hits the live backend; anything in §2
  (`NOT_ON_BACKEND`) still transparently falls back to mock data with a
  console warning, so those pages don't break outright — but expect real
  errors/empty states on pages that hit §3 (structurally unmapped, e.g.
  recovery/tracking, learning quiz) since those calls go out unmapped and
  will most likely 404 or mismatch. Test page by page rather than assuming
  the whole site works end to end yet.
- **OTP screen no longer accepts a blank submission.** It requires an
  actual 6-digit code client-side now. It also visibly says "Demo mode" —
  because the backend still has no `/auth/otp/*` routes (§2), any
  correctly-formatted code will still pass. That's not a frontend bug;
  it's an honest reflection of what's actually implemented server-side.
  Remove the note once those routes are live and `NOT_ON_BACKEND` is
  updated.

## Recommended order of attack

1. **Auth round-trip first.** Flip `USE_MOCKS = false` (or use `?live=1`),
   test login on `login.html`, and confirm the actual token field names in
   the network tab — fix `persistAuth`/`tryRefresh` per §3 if needed.
2. **Incidents (reports).** Fix the request-body shape (§3) so
   `report-incident.html` can actually submit.
3. **Read-only pages next** — dashboard, leaderboard, certificates, KYC
   status — these are mapped and mostly just need verification against
   real response shapes.
4. **Tackle the big structural gaps** (recovery/tracking, learning/quiz,
   community moderation, KYC draft flow) as their own scoped pieces of
   work, ideally with a shared decision on which side's shape wins.
5. **Backend feature gaps** (notifications, AI assistant, search, alerts,
   daily challenge, admin user management) — build these last, or decide
   which are actually needed for your competition demo vs. can stay mocked.
